# Специфікація вимог до програмного забезпечення (SRS)

**Система:** Платформа податкового обліку для ФОП із версіонуванням податкових правил
**Стандарт:** ISO/IEC/IEEE 29148:2018 (структура адаптовано для кваліфікаційної роботи)
**Версія:** 1.0 · **Статус:** Approved · **Джерело вимог:** [1_analysis.md](1_analysis.md), підрозділ 1.5

У цьому документі модальне дієслово «повинна» позначає обов'язкову вимогу. Кожна вимога має унікальний ідентифікатор і перевіряється методом, зазначеним у розділі 5.

## 1. Вступ

### 1.1. Призначення

Документ фіксує функціональні та нефункціональні вимоги до платформи й слугує контрактом між специфікацією, архітектурою ([2_design.md](2_design.md)) і верифікацією (розділ 3 пояснювальної записки).

### 1.2. Межі системи (Scope)

Платформа повинна забезпечувати облік доходів, звіряння банківських надходжень, розрахунок єдиного податку (ЄП), військового збору (ВЗ) і єдиного соціального внеску (ЄСВ) для ФОП 1–3 груп з вибором версії податкових правил за датою операції, а також аналіз впливу змін правил.

Поза межами системи: юридичні особи, ПДВ, податок на прибуток, подання звітності до Електронного кабінету ДПС з накладанням КЕП, мобільні застосунки, автоматичний розбір текстів нормативних актів.

## 2. Контекст системи (System Context)

### 2.1. Користувачі

| Роль | Опис | Канал доступу |
|---|---|---|
| ФОП (owner) | Власник профілю платника | Вебзастосунок (SPA) |
| Бухгалтер (accountant) | Делегований доступ до кількох профілів | Вебзастосунок (SPA) |
| Адміністратор правил (rules-admin) | Публікація версій податкових правил | Вебзастосунок, конвеєр CI репозиторію правил |

### 2.2. Зовнішні системи

| Система | Взаємодія | Протокол |
|---|---|---|
| API банків (відкритий банкінг, API окремих банків) | Отримання банківських операцій за згодою користувача | REST / HTTPS, OAuth 2.0 |
| Keycloak (Identity Provider) | Автентифікація, видача JWT | OpenID Connect / HTTPS |
| Репозиторій правил і GitHub Actions | Публікація перевірених версій правил | REST / HTTPS, сервісний токен |
| Поштовий сервер | Надсилання сповіщень | SMTP / TLS |
| Telegram Bot API | Надсилання сповіщень | REST / HTTPS |
| Електронний кабінет ДПС | Приймає XML-файл декларації, який користувач подає самостійно; прямої інтеграції немає | — |

### 2.3. Припущення та обмеження

- Демонстраційне розгортання виконується в одному кластері Kubernetes без географічного резервування.
- Банківські API можуть бути недоступні; система повинна зберігати працездатність інших функцій (див. [SRS-NFR-REL-05](#srs-nfr-rel-05)).
- Нормативні значення (мінімальна зарплата, ставки, ліміти) вводяться як параметри правил, а не як константи в коді.

## 3. Функціональні вимоги (Functional Requirements)

### 3.1. Identity & Tenant Service

- <a id="srs-fun-01"></a>**SRS-FUN-01.** Система повинна створювати окремий тенант для кожного зареєстрованого платника.
- <a id="srs-fun-02"></a>**SRS-FUN-02.** Система повинна призначати користувачу в межах тенанта одну з ролей: owner, accountant, rules-admin.
- <a id="srs-fun-03"></a>**SRS-FUN-03.** Система повинна надавати бухгалтеру доступ до профілю тенанта лише після підтвердження власником.
- <a id="srs-fun-04"></a>**SRS-FUN-04.** Система повинна обмежувати доступ до даних тенанта політиками Row-Level Security PostgreSQL.

### 3.2. Invoicing Service

- <a id="srs-fun-05"></a>**SRS-FUN-05.** Система повинна створювати рахунок-фактуру або акт виконаних робіт із реквізитами контрагента, сумою та призначенням.
- <a id="srs-fun-06"></a>**SRS-FUN-06.** Система повинна генерувати PDF-файл документа та зберігати його в об'єктному сховищі.
- <a id="srs-fun-07"></a>**SRS-FUN-07.** Система повинна змінювати статус оплати рахунку (виставлено, частково оплачено, оплачено) за подією звіряння.

### 3.3. Bank Ingestion & Reconciliation Service

- <a id="srs-fun-08"></a>**SRS-FUN-08.** Система повинна імпортувати банківські операції з файлів CSV за шаблонами банків.
- <a id="srs-fun-09"></a>**SRS-FUN-09.** Система повинна отримувати банківські операції через API банків за наданою користувачем згодою.
- <a id="srs-fun-10"></a>**SRS-FUN-10.** Система повинна відхиляти операцію, ключ ідемпотентності якої вже зареєстровано для тенанта.
- <a id="srs-fun-11"></a>**SRS-FUN-11.** Система повинна автоматично зіставляти надходження з рахунком за точним збігом суми, контрагента та номера рахунку в призначенні платежу.
- <a id="srs-fun-12"></a>**SRS-FUN-12.** Система повинна передавати до черги ручного підтвердження кандидатів нечіткого збігу з коефіцієнтом схожості призначення платежу від 0,85 до 1,00.
- <a id="srs-fun-13"></a>**SRS-FUN-13.** Система повинна обліковувати часткову оплату рахунку як суму підтверджених збігів.

### 3.4. Tax Engine Service

- <a id="srs-fun-14"></a>**SRS-FUN-14.** Система повинна обчислювати ЄП, ВЗ і ЄСВ за податковий період, вибираючи для кожної операції версію правил, чинну на дату операції.
- <a id="srs-fun-15"></a>**SRS-FUN-15.** Система повинна зберігати з кожним результатом розрахунку ідентифікатор версії правил і хеш SHA-256 вхідних даних.
- <a id="srs-fun-16"></a>**SRS-FUN-16.** Система повинна відтворювати розрахунок за збереженими ідентифікатором версії правил і вхідними даними.
- <a id="srs-fun-17"></a>**SRS-FUN-17.** Система повинна формувати XML-файл даних декларації платника ЄП, що відповідає XSD-схемі ДПС.
- <a id="srs-fun-18"></a>**SRS-FUN-18.** Система повинна публікувати подію при досягненні 80 %, 95 % і 100 % граничного обсягу доходу групи.

### 3.5. Rules Registry Service

- <a id="srs-fun-19"></a>**SRS-FUN-19.** Система повинна зберігати кожну версію податкового правила з періодом юридичної дії (valid time) і моментом реєстрації (transaction time).
- <a id="srs-fun-20"></a>**SRS-FUN-20.** Система повинна відхиляти будь-яку зміну опублікованої версії правила.
- <a id="srs-fun-21"></a>**SRS-FUN-21.** Система повинна виконувати тіньовий перерахунок для тенантів і періодів, яких стосується нова версія правил, без зміни основних результатів.
- <a id="srs-fun-22"></a>**SRS-FUN-22.** Система повинна формувати порівняльний звіт «було / стало» за результатами тіньового перерахунку.

### 3.6. Notification Service

- <a id="srs-fun-23"></a>**SRS-FUN-23.** Система повинна формувати податковий календар платника відповідно до його групи ЄП.
- <a id="srs-fun-24"></a>**SRS-FUN-24.** Система повинна надсилати сповіщення про строки сплати, подання звітності та пороги ліміту доходу каналами email і Telegram.

### 3.7. Наскрізні вимоги

- <a id="srs-fun-25"></a>**SRS-FUN-25.** Система повинна записувати до незмінного журналу аудиту кожну публікацію версії правил і кожне підтвердження перерахунку.

## 4. Нефункціональні вимоги (Non-Functional Requirements)

| ID | Категорія | Вимога |
|---|---|---|
| <a id="srs-nfr-perf-01"></a>SRS-NFR-PERF-01 | Продуктивність | Час відповіді API читання на p95 повинен не перевищувати 200 мс при навантаженні 200 RPS протягом 10 хв |
| <a id="srs-nfr-perf-02"></a>SRS-NFR-PERF-02 | Продуктивність | Час відповіді API створення рахунку на p95 повинен не перевищувати 300 мс при 50 RPS |
| <a id="srs-nfr-perf-03"></a>SRS-NFR-PERF-03 | Продуктивність | Частка відповідей з кодами 5xx повинна не перевищувати 0,5 % під навантаженням SRS-NFR-PERF-01 |
| <a id="srs-nfr-perf-04"></a>SRS-NFR-PERF-04 | Продуктивність | Імпорт файлу з 10 000 операцій до публікації подій повинен тривати не більше 30 с |
| <a id="srs-nfr-perf-05"></a>SRS-NFR-PERF-05 | Продуктивність | Затримка від імпорту операції до оновленого розрахунку на p95 повинна не перевищувати 5 с |
| <a id="srs-nfr-perf-06"></a>SRS-NFR-PERF-06 | Продуктивність | Тіньовий перерахунок для 1000 тенантів за 4 квартали повинен тривати не більше 10 хв |
| <a id="srs-nfr-scal-01"></a>SRS-NFR-SCAL-01 | Масштабованість | Сервіси без стану повинні масштабуватися Kubernetes HPA від 2 до 6 реплік при завантаженні CPU 70 % |
| <a id="srs-nfr-scal-02"></a>SRS-NFR-SCAL-02 | Масштабованість | Топіки Kafka повинні мати не менше 6 партицій із ключем `tenant_id` |
| <a id="srs-nfr-rel-01"></a>SRS-NFR-REL-01 | Надійність | Доступність публічного API повинна становити не менше 99,5 % за календарний місяць |
| <a id="srs-nfr-rel-02"></a>SRS-NFR-REL-02 | Надійність | Повторна доставка подій і повторний імпорт повинні створювати 0 дубльованих операцій |
| <a id="srs-nfr-rel-03"></a>SRS-NFR-REL-03 | Надійність | Недоступність брокера до 15 хв повинна не призводити до втрати подій; повторні спроби з експоненційною затримкою 1–60 с, після 5 спроб — Dead Letter Queue |
| <a id="srs-nfr-rel-04"></a>SRS-NFR-REL-04 | Надійність | Відновлення PostgreSQL на момент часу за 7 діб повинно забезпечувати RPO ≤ 15 хв і RTO ≤ 1 год |
| <a id="srs-nfr-rel-05"></a>SRS-NFR-REL-05 | Надійність | Після 5 послідовних помилок API банку Circuit Breaker повинен блокувати виклики на 60 с; інші функції повинні залишатися доступними |
| <a id="srs-nfr-rel-06"></a>SRS-NFR-REL-06 | Надійність | Кожен сервіс повинен надавати ендпоінти liveness і readiness, що використовуються Kubernetes |
| <a id="srs-nfr-cor-01"></a>SRS-NFR-COR-01 | Коректність | 100 % розрахунків повинні відтворюватися з ідентичним результатом; публікація версії правил блокується без успішних golden tests |
| <a id="srs-nfr-cor-02"></a>SRS-NFR-COR-02 | Коректність | Грошові суми повинні оброблятися типом `Decimal` з округленням до копійки за правилом ROUND_HALF_UP; тип `float` заборонено |
| <a id="srs-nfr-sec-01"></a>SRS-NFR-SEC-01 | Безпека | Автентифікація повинна виконуватися за OAuth 2.0 / OpenID Connect (Keycloak); access token — JWT RS256 з терміном дії 15 хв, refresh token — 8 год |
| <a id="srs-nfr-sec-02"></a>SRS-NFR-SEC-02 | Безпека | Авторизація повинна виконуватися за ролями (RBAC) з політикою deny-by-default |
| <a id="srs-nfr-sec-03"></a>SRS-NFR-SEC-03 | Безпека | Політики RLS повинні забезпечувати 0 успішних звернень до даних іншого тенанта |
| <a id="srs-nfr-sec-04"></a>SRS-NFR-SEC-04 | Безпека | Зовнішній трафік повинен використовувати TLS 1.3; поля IBAN і РНОКПП повинні шифруватися AES-256-GCM |
| <a id="srs-nfr-sec-05"></a>SRS-NFR-SEC-05 | Безпека | API Gateway повинен обмежувати 100 запитів за хвилину на користувача та повертати HTTP 429 при перевищенні |
| <a id="srs-nfr-sec-06"></a>SRS-NFR-SEC-06 | Безпека | Код і образи повинні відповідати OWASP ASVS 4.0 L2: SonarQube — 0 Blocker/Critical, Bandit — 0 High, Trivy — 0 Critical CVE |
| <a id="srs-nfr-sec-07"></a>SRS-NFR-SEC-07 | Безпека | Секрети повинні зберігатися в Kubernetes Secrets; конвеєр CI повинен блокувати коміти із секретами (gitleaks) |
| <a id="srs-nfr-cmp-01"></a>SRS-NFR-CMP-01 | Комплаєнс | Обробка персональних даних повинна відповідати Закону «Про захист персональних даних»; дані тенанта повинні видалятися протягом 30 днів після запиту, крім даних, що зберігаються 1095 днів для податкових цілей |
| <a id="srs-nfr-aud-01"></a>SRS-NFR-AUD-01 | Аудит | Журнал аудиту повинен бути append-only і зберігатися не менше 1095 днів |
| <a id="srs-nfr-obs-01"></a>SRS-NFR-OBS-01 | Спостережуваність | Трасування OpenTelemetry повинно охоплювати 100 % запитів з помилками та не менше 10 % успішних |
| <a id="srs-nfr-obs-02"></a>SRS-NFR-OBS-02 | Спостережуваність | Логи повинні мати формат JSON з полями `trace_id` і `tenant_id`; сповіщення повинні спрацьовувати при відставанні консюмера понад 1000 повідомлень протягом 5 хв |
| <a id="srs-nfr-mnt-01"></a>SRS-NFR-MNT-01 | Супроводжуваність | Покриття тестами доменних модулів повинно становити не менше 80 %; mypy у режимі strict повинен завершуватися без помилок |
| <a id="srs-nfr-mnt-02"></a>SRS-NFR-MNT-02 | Супроводжуваність | Публічне API повинно мати префікс версії `/api/v1` і специфікацію OpenAPI 3.1 |
| <a id="srs-nfr-inf-01"></a>SRS-NFR-INF-01 | Інфраструктура | Сервіси повинні запускатися в контейнерах Docker від непривілейованого користувача та розгортатися Helm; конвеєр CI повинен тривати не більше 15 хв |

## 5. Критерії верифікації (Verification Criteria)

| Вимоги | Метод | Інструмент і критерій проходження |
|---|---|---|
| SRS-FUN-01 – SRS-FUN-03 | Тест | Інтеграційні тести pytest + Testcontainers (PostgreSQL, Keycloak); API-сценарії Postman/Newman |
| SRS-FUN-04, SRS-NFR-SEC-03 | Тест | pytest: запити від імені тенанта A до даних тенанта B повертають 0 рядків |
| SRS-FUN-05 – SRS-FUN-07 | Тест | pytest; перевірка PDF у MinIO (Testcontainers) |
| SRS-FUN-08 – SRS-FUN-10, SRS-NFR-REL-02 | Тест | pytest: повторний імпорт того самого файлу та повторна доставка події не змінюють кількість операцій |
| SRS-FUN-11 – SRS-FUN-13 | Тест | pytest на еталонному наборі з 500 операцій із відомими збігами; точність автоматичного збігу ≥ 95 % |
| SRS-FUN-14 – SRS-FUN-16, SRS-NFR-COR-01 | Тест | Golden tests для кожної версії правил; property-based тести Hypothesis: повторний розрахунок дає ідентичний хеш і суму |
| SRS-FUN-17 | Тест | Валідація XML за XSD-схемою ДПС (lxml) |
| SRS-FUN-18, SRS-FUN-23, SRS-FUN-24 | Тест | pytest з фіксованим часом (freezegun); тестовий SMTP-сервер (Mailpit) |
| SRS-FUN-19 – SRS-FUN-22 | Тест | pytest: спроба UPDATE опублікованої версії повертає помилку; тіньовий перерахунок не змінює основні результати |
| SRS-FUN-25, SRS-NFR-AUD-01 | Інспекція | Перевірка схеми: таблиця журналу без привілеїв UPDATE/DELETE для ролі застосунку |
| SRS-NFR-PERF-01 – SRS-NFR-PERF-03 | Тест навантаження | k6: сценарії constant-arrival-rate (10 хв) і spike; пороги `http_req_duration{p(95)}` та `http_req_failed < 0.005` |
| SRS-NFR-PERF-04 – SRS-NFR-PERF-06 | Тест | Інтеграційний тест з генератором даних; тривалість за трасами OpenTelemetry (Jaeger) |
| SRS-NFR-SCAL-01, SRS-NFR-SCAL-02 | Демонстрація | Масштабування під k6-навантаженням; `kubectl get hpa`, опис топіків Kafka |
| SRS-NFR-REL-01 | Аналіз | Метрика доступності в Prometheus, панель Grafana |
| SRS-NFR-REL-03, SRS-NFR-REL-05 | Тест відмови | Зупинка контейнера Kafka / заглушки банку в Testcontainers; перевірка Outbox і DLQ |
| SRS-NFR-REL-04 | Демонстрація | Відновлення бази з архіву WAL у тестовому середовищі з фіксацією часу |
| SRS-NFR-REL-06 | Інспекція | Helm-маніфести: `livenessProbe`, `readinessProbe` |
| SRS-NFR-COR-02 | Аналіз | Правило статичного аналізу (Ruff, SonarQube) та тести меж округлення |
| SRS-NFR-SEC-01, SRS-NFR-SEC-02 | Тест | Postman/Newman: прострочений, змінений або чужий JWT → HTTP 401/403 |
| SRS-NFR-SEC-04 | Інспекція | Конфігурація API Gateway; `testssl.sh`; тест шифрування полів |
| SRS-NFR-SEC-05 | Тест навантаження | k6: 120 запитів за хвилину від одного користувача → частка HTTP 429 |
| SRS-NFR-SEC-06, SRS-NFR-SEC-07 | Аналіз | SonarQube Quality Gate, Bandit, Trivy, gitleaks у GitHub Actions |
| SRS-NFR-CMP-01 | Тест | pytest сценарію видалення тенанта |
| SRS-NFR-OBS-01, SRS-NFR-OBS-02 | Демонстрація | Jaeger, Loki, правила сповіщень Prometheus Alertmanager |

## 6. Глосарій (Glossary)

| Термін | Визначення |
|---|---|
| Бітемпоральна модель | Модель даних, у якій кожен запис має період юридичної дії (valid time) і момент реєстрації в системі (transaction time) |
| Transactional Outbox | Патерн, за якого подія записується в таблицю outbox у тій самій транзакції, що й зміна даних, і публікується в брокер окремим процесом |
| Ключ ідемпотентності | Детермінований ідентифікатор операції, за яким повторна обробка того самого повідомлення не змінює стан системи |
| Eventual Consistency | Модель узгодженості, за якої стан різних сервісів стає узгодженим через обмежений час після обробки подій |
| CQRS | Розділення моделі запису та моделі читання даних |
| JWT | JSON Web Token — підписаний токен із заявами (claims) про користувача та його ролі |
| Latency p95 | Значення часу відповіді, яке не перевищують 95 % запитів |
| Тенант | Ізольований простір даних одного платника; ізоляція забезпечується Row-Level Security |
